# Поступашки — Marketing Measurement MVP

Каркас системы, которая должна сделать измеримым путь:

`размещение рекламы → переход → действие на сайте → обращение к менеджеру → заказ → оплата`.

Сейчас это работающий end-to-end MVP на синтетических данных: tracking-ссылка фиксирует рекламный клик, события сайта связываются с лидом, заказом и оплатой, атрибуция относит выручку к размещению, а API и Streamlit-дашборд показывают единую воронку и сравнение кампаний.

## Что входит в первую версию MVP

1. Реестр кампаний и рекламных размещений.
2. Генерация уникальной tracking-ссылки для `placement_id`.
3. Приём событий клика и действий на сайте.
4. Связывание анонимного посетителя с лидом через идентификатор в ссылке/заготовленном сообщении менеджеру.
5. Загрузка заказов и оплат.
6. Last-touch, first-touch и linear атрибуция в окне 30 дней.
7. Расчёт воронки, CAC, CPL, CPO и `ROMI_attr`.
8. Проверки качества данных и разделение real/synthetic.
9. Аналитический API и дашборд на общей расчётной логике.

Исторический `base.xlsx` анализируется отдельно в ноутбуке: он описывает продажи, но не содержит касаний и поэтому не используется для доказательства эффективности каналов.

## Что добавляется позже без смены ядра

- Telegram collector и автоматическое обнаружение постов;
- NLP-классификация постов;
- time-decay и data-driven модели атрибуции;
- эксперименты и incremental ROMI;
- прогнозирование и рекомендации по бюджету;
- PostgreSQL вместо SQLite;
- Superset вместо или вместе со Streamlit.

Эти компоненты подключаются новыми таблицами, сервисами и миграциями. Основные сущности `campaign`, `placement`, `event`, `lead`, `order`, `payment` сохраняются.

## Быстрый запуск

Требуется Python 3.11+.

```powershell
python -m pip install -e ".[dev]"
python scripts/init_db.py
python scripts/seed_demo.py
uvicorn postupashki_mvp.api:app --reload
```

Swagger API: `http://127.0.0.1:8000/docs`.

Основные аналитические методы:

- `/analytics/summary` — сводка бизнеса;
- `/analytics/campaigns` — сравнение кампаний;
- `/analytics/funnel` — общая воронка или срез по `campaign_id`;
- `/analytics/placements` — эффективность размещений;
- `/data-quality/summary` — конкретные ошибки и предупреждения данных.

Для них доступны параметры `data_kind=synthetic|real`,
`attribution_model=last_touch|first_touch|linear` и необязательный `campaign_id`.

Дашборд:

```powershell
streamlit run src/postupashki_mvp/dashboard/app.py
```

Синтетический сценарий создаёт 3 кампании и 6 размещений с разными расходами, конверсиями и ценами продуктов. В дашборде можно выбрать тип данных, модель атрибуции и одну кампанию, изучить её воронку и сравнить кампании по выручке, расходам, CAC и ROMI. Один тестовый посетитель касается двух кампаний, поэтому переключение модели атрибуции действительно меняет распределение результата.

Тесты:

```powershell
pytest
```

## Порядок дальнейшей разработки

1. Подключить бизнес-интерфейс к готовому аналитическому API.
2. Добавить time-decay модель атрибуции, если она нужна для демонстрации.
3. Реализовать планировщик экспериментов и `ROMI_inc`.
4. Добавить сценарий распределения следующего рекламного бюджета.

## Правила данных

- Реальные и синтетические данные нельзя смешивать без признака `is_synthetic`.
- Сырые события не перезаписываются; исправления делаются отдельными записями или миграциями.
- Telegram ID, телефон и username не хранятся в аналитическом слое открытым текстом.
- Метод и версия атрибуции всегда фиксируются вместе с результатом.
- Схема БД меняется только через версионируемые миграции.
